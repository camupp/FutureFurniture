# MVP FutureFurniture — техническая карта реализации

> Обновлено: 27 сентября 2026 года.
> Статус: рабочая карта решений и экспериментов, не фиксированное ТЗ.
> Новые сущности и API ниже — предложения, а не описание уже существующего кода.
> Документ не разрешает автоматически реализовать весь план: объём каждой задачи
> определяется актуальным запросом пользователя.

## 0. Контекст за две минуты

Пользователь — замерщик на объекте. Результат — быстро полученный, понятный клиенту
и редактируемый 2D/3D-эскиз кухни, а не производственные чертежи.
Итоговый MVP включает ИИ-планировщика. Ручной редактор остаётся полноценным способом работы.

Ключевые решения:

1. Каталог описывает смысл, допустимые конфигурации и размещение модулей, не только meshes.
2. Размеры гибридные: предпочтительные варианты плюс разрешённая подгонка;
   техника не растягивается, доборы учитываются при расчёте ряда.
3. Шаблон — правила состава и адаптации. Схема рядов, функциональные решения
   и оформление разделены.
4. ИИ переводит намерение в проверяемые требования/команды. Точные координаты
   вычисляет алгоритм; допустимость проверяет ядро, не текст ответа модели.
5. Ручная расстановка и генератор переиспользуют геометрию и каталоговые правила.
   Генератор не является циклом вызовов drag-and-drop магнита.
6. Результат сначала показывается как предложение. Принятие — одно атомарное
   изменение с Undo; ручные фиксации и чужой активный проект защищены.
7. Начинаем с одного сквозного сценария прямой кухни. Не ждём полного каталога,
   чтобы проверить требования, генерацию, принятие и одну диалоговую правку.
8. До полевого пилота нужны именованные варианты, объектные замечания,
   список модулей и наблюдаемость. Это не повод строить CRM, ERP или облачный CAD.

### Как пользоваться картой

- Сначала понять текущую задачу и прочитать соответствующие разделы, а не превращать
  весь документ в список обязательных изменений.
- Сохранять цель и пользовательские гарантии; пересматривать порядок работ,
  алгоритмы, типы, границы файлов и инструменты при появлении новых данных.
- Не создавать абстракцию только потому, что она названа ниже. Каждая сущность
  должна помогать текущему проверяемому сценарию.
- Если более простой путь даёт тот же результат, выбрать его и записать причину.
- Изменение технической детали не требует отдельного согласования каждого шага;
  изменение аудитории, обещаний продукта, существенного scope или внешних расходов —
  повод обсудить решение с пользователем.

## 2. Что выборочно перенимаем из Cyncly

Разбор прочитан целиком. Для ключевых выводов также сверены официальные
[R48](https://is.support.cyncly.com/hc/en-us/articles/50254919530129--Spaces-Flex-R48-Release-Notes-August-2026),
[R49](https://is.support.cyncly.com/hc/en-us/articles/51016853317137--Spaces-Flex-R49-Release-Notes-September-2026)
и [R44](https://is.support.cyncly.com/hc/en-us/articles/46653064321937--Spaces-Flex-R44-Release-Notes-May-2026).
Они описывают условия до генерации/подгонку доборов, объектную валидацию
и дублирование дизайнов. Конкретный solver и его детерминизм публично не установлены:
дальнейшая архитектура — наше решение, не реконструкция исходников Cyncly.

| Наблюдение / рекомендация из разбора                   | Решение для нашего MVP                                                                      |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| Важные приборы и выводы задаются до генерации          | Короткая сводка требований с подтверждением; не обязательное ручное размещение всей техники |
| Каталог задаёт поведение размещения                    | Способ установки, поверхности/опоры, отступы и совместимость в общем профиле                |
| Smart placement развивается независимо от Auto Design  | Сохраняем удобную ручную работу; объединяем примитивы, не переписываем всё в один алгоритм  |
| Замечание ведёт к конкретному объекту                  | Типизированные ссылки, подсветка, объяснение, актуальность по ревизии                       |
| Другие предложения и копии дизайнов                    | Временные кандидаты плюс сохраняемые именованные копии, без веток и merge                   |
| Структурированный результат для следующего специалиста | Производный перечень модулей и пакет эскиза, не BOM каждой петли                            |
| Сложности с presets, сохранением и асинхронностью      | Транзакции, контроль ревизии, безопасный отказ, сценарные регрессии                         |

Не принимаем автоматически:

- Расширение аудитории до retail/самостоятельного покупателя.
- RBAC, систему capabilities и иерархию Project → Designs → Versions до реальной потребности.
- Factory/SKU/pricing/inventory/lifecycle-сервисы как предпосылку генератора.
- LiDAR, vision, AI beautify, CRM и kiosk.
- Строго «минимум два варианта»: честно показать один, если других не нашли.
- PDF при каждом autosave: экспорт по запросу из согласованного снимка.
- Метрики только после пилота: простые измерения нужны уже в прототипе.

Конкурентные кейсы не доказывают спрос у наших замерщиков. Необнаруженная в
публичной документации функция не считается гарантированно отсутствующей.

Срез 27.09.2026: [cabinetFamilies.ts](../src/domain/modules/cabinetFamilies.ts)
содержит определения `base-storage@1`, `wall-storage@1`, `tall-storage@1` с
назначением, типовыми/допустимыми размерами и собственными фасадными схемами.
Это иллюстративные размеры MVP, не производственный каталог. Новые экземпляры
хранят ID, версию и выбор фасада. Старые тестовые шкафы без метки семейства
при загрузке ориентировочно переводятся на одно из новых семейств по высоте и
отметке над полом; точность такого переноса не гарантируется. IndexedDB и JSON
не удаляются автоматически. Реальные ящики, петли и фурнитура не моделируются.

[cabinetFaces.ts](../src/domain/assemblies/cabinetFaces.ts) вычисляет видимые
фасадные панели и ручки в локальных миллиметрах. 3D и «Фасад стены» используют
один результат; закрытая часть глухого угла остаётся без фасада в обоих видах.
У пенала доступны две дверцы по высоте (по умолчанию) или одна высокая с
ручкой на доступной высоте; у навесного шкафа — одна/две дверцы или эскиз
подъёмного фасада. Положение фасадов и ручек вычисляется в общих локальных
координатах для 3D и «Фасада стены». Скоба/кнопка и сторона ручки выбираются
на экземпляре. Подъёмный фасад пока не анимируется, зоны его открывания не
проверяются; формы ручек не содержат артикула, отверстий или цены.

Срез 28.09.2026: [straightKitchen.ts](../src/domain/generation/straightKitchen.ts)
строит один прямой ряд на выбранной внешней стене. Короткая форма задаёт мойку,
тип кухонной плиты, духовку, посудомойку, холодильник, минимум рабочей поверхности
и приоритет хранения. Ограниченный детерминированный перебор проверяет физические
препятствия существующими правилами, допускает одну подгоняемую базу хранения и
добавляет промежуточные базы между зонами мойки и плиты. Посудомойка остаётся
рядом с мойкой, но может стоять с любой стороны. Из допустимых кандидатов сначала
выбирается тот, который покрывает больше требований отмеченными выводами газа,
воды, канализации и питания с учётом радиуса розеток и числа гнёзд; газовый вывод
проверяется по эскизному радиусу 800 мм до задней сервисной зоны плиты, а не
только по высоте нижней базы. Затем
сравниваются прочие предупреждения, расстояния и предпочтение хранения.
Неотмеченный вывод остаётся неизвестным, а не считается физическим запретом.
Если отмеченный вывод не подходит ни к одному доступному варианту, панель
показывает число несовпавших требований и оставляет предупреждение явным.
Предложение показывается на плане и в 3D без записи в проект. Принятие через
[generatorSlice.ts](../src/application/project/slices/generatorSlice.ts) проверяет
актуальность исходного документа и активного проекта, заменяет временные ID и добавляет ряд с техникой
и автостолешницей одним undoable изменением. Мойка/плита при загрузке больше не
получают ошибочно угаданную привязку к стене. Роли базы под мойку/панель
запрещают фасад с ящиками, а база/пенал с духовкой, посудомойка и встроенный
холодильник имеют отдельные эскизные фронты. Проверки выводов и свободной зоны
перед техникой не доказывают реальные монтажные зазоры, электрическую мощность
и путь труб.

Это прототип одного сценария, не полный адаптивный шаблон: нет фиксации модулей,
локальной перестройки, сохраняемых альтернатив, полноценной проверки пригодности
техники и диалога. Предупреждение о коммуникации — не инженерное заключение.

### Ловушки расширения

1. Добавленное только в store поле может исчезнуть при загрузке: projectSchema
   содержит room/furniture, а неизвестные поля Zod не становятся частью модели.
2. Требования/фиксации/стили вне этих полей не попадут автоматически в историю,
   partialize, подписку сохранения и JSON.
3. historyRevision — сигнал Undo/Redo/загрузки, **не ревизия каждого изменения**.
   updatedAt записи IndexedDB также не годится для защиты позднего ответа.
4. Нижняя база для столешницы определяется эвристикой типа/высоты. Новая ниша
   техники или открытая секция потребует явной семантики опоры.
5. Мойка/плита исключены из обычных столкновений; это не проверка правильной установки.
6. Загрузка может нормализовать старые связи и позиции. Такой repair-путь нельзя
   бездумно применять к новому предложению: он способен скрыть ошибку генератора.
7. Несколько частей L-столешницы — не несколько независимых товарных изделий.
8. Domain не может импортировать UI-каталог из features. Общие определения
   должны быть доступны без React, Konva, Three, Zustand и браузерного хранилища.

Не требуется новый большой архитектурный рефакторинг. Расширяем существующее
вычислительное ядро и команды постепенно, соблюдая проверяемые границы.

## 4. Предлагаемая модель: смысловые контракты, не окончательные типы

Имена ниже условны. Начальный срез может реализовать несколько понятий одним
простым модулем. Не создавать отдельную директорию/сервис на каждую строку.

### 4.1. Определение семейства и экземпляр

**ModuleFamily**: стабильный ID и версия, назначение, допустимые конфигурации,
размерная политика, способ установки, отступы, правила опоры/совместимости,
доступные варианты оформления. Каталог не содержит выполняемый код от модели.

**ModuleInstance**: ID объекта, ссылка на семейство/версию, фактически выбранные
размеры, конфигурация, положение, привязка, пользовательские исключения оформления.
Ссылка на каталог не заменяет сохранение принятого результата.

Существующие cabinet не нужно сразу конвертировать в множество BlockType.
Рабочая гипотеза — оставить базовый тип геометрии, добавить отдельную идентичность
семейства/конфигурации. Пересмотреть, если рендер и правила от этого усложняются.

Для текущего однопользовательского прототипа принято сознательное упрощение:
старые тестовые шкафы без метки семейства при загрузке интерпретируются по
высоте/отметке через новые семейства, поэтому их вид может измениться. Это не
политика миграции реальных пользовательских проектов. Перед пилотом её нужно
пересмотреть: версия каталога или сохраняемый snapshot определения должны
гарантировать открытие проекта после изменения фасадных правил.

### 4.2. Три разных вида «секций»

- **FacadeSection** — область фасада модуля: дверца, ящик, открытая часть,
  пропорция/размер и способ открывания.
- **ApplianceMount** — место установки техники: назначение, локальный объём,
  требования к вырезу/опоре и связь с выбранным прибором.
- **TemplateRole** — роль модуля в решении: мойка, хранение, посудомойка и т. п.

Не объединять их в универсальный slot с неоднозначным смыслом.
Для MVP фасадные схемы ограничены готовыми вариантами, не рекурсивным CAD-деревом.
Отдельные ID секций нужны, когда их выбирают/редактируют независимо, не заранее.

### 4.3. Ряды, шаблоны и оформление

**Run**: локальный origin, направление, полезная длина/интервалы, сторона фасада,
уровень установки и необязательная связь со стеной. Пользовательская «верхняя группа»
и нижний ряд могут иметь общую схему, но разные ограничения по высоте.

Нужно различить: найденный геометрический ряд существующих тумб и намерение
планировщика собрать определённый ряд. Не создавать второй независимый источник
координат. При сохранении планового ряда его связь с реальными объектами должна
обновляться командами; иначе лучше оставить его временным входом генератора.

**LayoutTemplate**: условия применимости, схема рядов, функциональные роли,
возможные замены, опциональные части и приоритеты адаптации.
**StylePreset**: только разрешённые варианты оформления.
Разные цвета одной кухни не требуют отдельных алгоритмов генерации.

Стиль наследуется: кухня → группа → экземпляр. Выбор новой темы не стирает
индивидуальные исключения без явного действия. Изменение материала визуальное;
изменение ручки/открывания может потребовать пересчёта физических ограничений.

### 4.4. Требования и фиксации

**KitchenRequirements**: предпочтение схемы, обязательная техника, приоритеты,
подтверждённые предположения и неизвестные данные. Коммуникации ссылаются на
объекты комнаты, а не копируются в отдельную расходящуюся геометрию.

Обязательность и достоверность независимы. «Посудомойка обязательна, модель
не выбрана» означает обязательную роль с предварительным размерным профилем,
а не разрешение удалить её или объявить подключение проверенным.

**PlacementLock**: адрес объекта и зафиксированные аспекты — позиция, размер,
назначение/конфигурация. Гипотеза MVP: замок ограничивает автоматические изменения,
а явная ручная правка подтверждает новое решение; точную UX-семантику проверить.

Для пристенного объекта различать фиксацию в мировой системе и фиксацию
смещения относительно стены. Если пользователь меняет стену и условия конфликтуют,
не нарушать фиксацию молча. На первом этапе можно поддержать один явно названный режим.

### 4.5. Производные и временные данные

- Фактическая геометрия/конфигурация, требования, фиксации и принятые предположения —
  данные документа, если влияют на последующие действия.
- Render meshes, проекции, актуальные ошибки и перечень модулей — производные
  представления конкретной ревизии.
- Генерируемые кандидаты, ожидание ответа, hover, камера — временные данные.
- Сохранённый вариант — самостоятельный документ, не объект Undo и не временный кандидат.

Не хранить вычисленные warnings как вечную истину. Сохранять подтверждённые
замечания пользователя отдельно; отчёт проверок при необходимости имеет
ревизию/версии правил и после изменений явно устаревает.

## 5. Общее ядро правил и размещения

### 5.1. Геометрический контракт

Сохраняем системы координат текущего редактора: план x вправо, y вниз,
rotation в градусах по часовой стрелке, elevation — низ блока над полом.
Модель использует миллиметры; Three переводит их в метры на своей границе.
Промежуточные расчёты могут быть дробными: не округлять каждый шаг и не путать
численную погрешность с технологическим зазором или пользовательским шагом размера.

Для конфигурации выводятся:

- Корпусной габарит для размеров и привязки.
- Физические занимаемые объёмы, включая значимые выступы.
- Опорные/монтажные области встроенной техники.
- Зоны открывания и обслуживания в упрощённой модели.
- Разрешённые поверхности/соединения и начальные отступы установки.

Ручки не должны неожиданно менять точку привязки корпуса. Но их выступ может
влиять на открывание соседнего фасада. Зоны доступа не равны сплошным телам:
совпадение двух таких зон не всегда означает коллизию, политика задаётся правилом.

Текущая модель пола поддерживает ограниченный тип контура. Генератор сначала
проверяет поддерживаемость помещения; не превращает неподдерживаемую геометрию
в «кухня невозможна» и не чинит комнату без согласия.

### 5.2. Слои проверки

1. **Формат:** версии, типы, конечные числа, допустимые размеры входа.
2. **Структура:** уникальность ID в выбранном пространстве, существование
   ссылок, корректные типы host/support/wall, отсутствие недопустимых циклов.
3. **Каталог:** существующие family/config/style IDs, размерные политики,
   совместимость приборов и конфигураций.
4. **Геометрия/функция:** стены, проёмы, опоры, открывание, известные ограничения.
5. **Требования:** обязательные роли, фиксации и границы области редактирования.
6. **Итог:** повторная проверка после синхронизации столешниц, доборов и других сборок.

Предложение с ошибочной ссылкой отклоняется, а не «восстанавливается» эвристикой
импорта. У legacy-импорта отдельная политика восстановления с сохранением оригинала.

### 5.3. Диагностика как данные

Рекомендуемый смысл результата правила:

- Стабильный code/ruleId и версия правила.
- Типизированные objectRefs; номер в списке — подпись, не идентичность.
- Серьёзность сообщения и отдельный статус проверки: конфликт, предупреждение,
  неизвестно, не применимо. Обязательность требования хранится отдельно.
- Измеренные значения, причина и сведения, которых не хватает.
- Допустимые предложения исправления как команды, не автоматически исполненные действия.
- Ревизия документа и область выполненной проверки.

UI показывает связанные объекты на плане/в 3D через существующее выделение
или временную подсветку, не меняя геометрию. Отсутствующая модель не прячется
за зелёным общим статусом. Объяснение ИИ опирается на эти данные, а не заменяет их.

### 5.4. Где объединять, а где не объединять

Общие: footprints, wall frames, допустимые интервалы, каталоговые ограничения,
создание экземпляров, нормализация и валидация.
Разные: интерактивный preview магнита, точный числовой ввод и поиск всей кухни.

Не вести последовательность генерации через addBlock/dropFurniture:
магнит изменит рассчитанный результат, а подписчики увидят промежуточные состояния.
Результат генератора — подготовленный документ/patch, который можно проверить целиком.

## 6. Генератор: от малого поиска к адаптивным решениям

### 6.1. Минимальный вход и выход

Вход — неизменяемый снимок комнаты и текущих объектов, область изменений,
структурированные требования, фиксации, профиль каталога, версии правил/шаблонов
и настройки ограниченного поиска. Внешний newId/seed задаётся явно, если нужен.

Выход не должен быть просто массивом мебели. Нужны кандидаты, выполненные проверки,
предположения, измеренные компромиссы и статус:

- Найдены допустимые кандидаты в рамках известных данных.
- Нужны уточнения.
- Некорректный вход.
- Неподдерживаемый сценарий.
- Поиск остановлен по лимиту/отменён.
- Установлен конфликт обязательных условий.

Последний статус требует основания в поддерживаемой модели: неудача эвристики
не доказывает невозможность. Если найден кандидат, но оптимальность не доказана,
не называть его оптимальным.

### 6.2. Подбор прямого ряда

Рабочий алгоритм первой версии:

1. Нормализовать требования; отделить подтверждённые значения от допущений.
2. Найти выбранный ряд и доступные интервалы на нужной высоте, учесть соседние
   стены/проёмы и неизменяемую мебель.
3. Зарезервировать фиксированные элементы, торцевые панели, нужные зазоры и доборы.
4. Перебрать небольшой набор функциональных последовательностей, не все
   перестановки любых модулей.
5. Подобрать предпочтительные ширины; при разрешении — bounded-размеры по шагу.
   Габариты техники/монтажной ниши не масштабировать вместе с остатком ряда.
6. Превратить позиции вдоль ряда в мировые координаты и собрать candidate.
7. Синхронизировать производные сборки вне live-store; проверить весь результат.
8. Среди допустимых ранжировать по предпочтениям и устойчивости относительно
   текущего эскиза; удалить эквивалентные варианты.

Остаток длины — не всегда ошибка и не всегда добор. Учитывать допустимое место,
диапазон и назначение добора. Сумма модулей, панелей, резервов и зазоров
должна соответствовать принятой модели полезной длины без двойного учёта.

Сначала достаточно ограниченного перебора/динамического программирования
в чистых TypeScript-функциях. Конкретный алгоритм выбираем по небольшому корпусу
задач. Не подключаем промышленный solver ради одной строки из фиксированных модулей.

### 6.3. Г-образная схема и альтернативы

Угол связывает полезные длины обоих рядов: нельзя решить их независимо,
а затем просто наложить две кухни. Угловое правило резервирует глухую часть,
доступный фасад, отступы и совместимые варианты соседних модулей.
Переиспользовать расчёты cabinetJoints/countertops, но проверить их пригодность
для поиска: визуальное срастание не равно допустимому открыванию.

Варианты отличаются составом/распределением зон или измеримым компромиссом,
а не UUID или несущественным сдвигом. Например, больше непрерывной рабочей зоны
либо больше хранения. До появления достоверного расчёта объёма хранения
использовать честно названный proxy-показатель, не выдумывать литры или проценты.

Предпочтения ранжируют только допустимые результаты. Большой вес «красоты»
не может компенсировать нарушение обязательного требования.
Порядок tie-break стабилен; при случайном поиске записывается seed.
Воспроизводимость относится к структурированному входу генератора,
не к буквальному тексту каждого ответа языковой модели.

### 6.4. Частичная перестройка

Область редактирования — выбранный ряд или интервал между опорными объектами.
Вне области объекты остаются неизменными и участвуют в проверке как препятствия/опоры.
«Не зафиксирован» не означает «разрешено изменить в любой части кухни».

Сборки могут пересекать область: общая столешница, цоколь, стык соседнего ряда.
Их затронутые зависимости включаются в diff и проверяются. Если выполнить запрос
без расширения области нельзя, объяснить это до применения.
Сохранять ID неизменённых объектов; новая UUID всей кухни затруднит фиксации,
сравнение вариантов и выбор объектов.

Рабочая политика существующих ошибок: ручной черновик может содержать известные
геометрические конфликты. Локальная правка проверяет затронутую область и её зависимости,
не создаёт новых и не усиливает старые нарушения, но не обязана чинить посторонний
неизменённый конфликт. Его продолжают показывать; весь проект не объявляется валидным.
Сравнивать проблемы по правилу, объектам и измеренному нарушению, не только по количеству.
Полная генерация проверяет весь результат в поддерживаемой области. Структурно
некорректные данные требуют отдельного восстановления, а не такого послабления.
Эту UX-политику проверить на сценарии «замена ящиков при старой ошибке в другом ряду».

## 7. Предложение изменений и атомарное принятие

Это общий механизм для формы, агента и будущей замены каталожных позиций.
Не нужен универсальный event-sourcing framework; нужна ясная граница draft/commit.

### 7.1. Рекомендуемый контракт предложения

- proposalId/requestId и projectId выбранного самостоятельного варианта.
  Отдельный designId нужен только при появлении вложенной иерархии дизайнов.
- Исходная ревизия документа либо hash всех значимых входов.
- Область и намерение изменения.
- Изменённые/добавленные/удалённые объекты, включая производные последствия.
- Принятые требования, предположения, версии каталога/шаблона/правил.
- Результаты проверки и вычисленные различия между вариантами.

Формат patch против полного candidate выбирается по простоте реализации.
Даже полный candidate не получает право менять объекты вне разрешённой области.
Не принимать от LLM произвольные JSON-path записи в store.

### 7.2. Жизненный цикл

1. Зафиксировать входной снимок и токен текущего документа.
2. Построить и проверить candidate вне активного состояния.
3. Показать preview и diff; изменение выбранного preview не вызывает autosave.
4. При принятии проверить проект, актуальность входа, фиксации, ссылки и область.
5. Получить окончательно синхронизированный документ и проверить его ещё раз.
6. Опубликовать его одним application-действием: один шаг истории и согласованное
   уведомление подписчиков; обычная сессия выполняет автосохранение.

Не рассчитывать производные ID заново отличающимся способом между preview и commit.
Возможные решения: использовать тот же подготовленный снимок либо стабильную
фабрику ID. Следовать существующему принципу восстановления готового Undo-снимка.

Ошибки, отмена и отклонённое предложение не меняют live-document.
Повторное нажатие «Применить» не дублирует мебель. Это обеспечивается статусом
предложения/idempotency и контролем ревизии, а не надеждой на disabled-кнопку.

### 7.3. Актуальность

Нужен новый документный revision/token либо hash, покрывающий room, furniture,
requirements, locks, styles и используемые версии каталога. Изменение UI-камеры
само по себе не обязано инвалидировать геометрическое предложение.
При Undo/Redo/загрузке revision не откатывается вместе с содержимым.
Вариант с hash требует также контроля projectId и жизненного цикла запроса.

Простая политика MVP: устаревшее предложение отклонить и предложить пересчитать.
Автоматический rebase пока не нужен. Отмена сетевого запроса полезна,
но контроль токена обязателен даже если поздний ответ всё-таки пришёл.

## 8. Срезы A–C: проверочные задачи, прототип, конфигурируемые модули

Буквы обозначают направления, а не жёсткую последовательность. Каждый срез
должен давать проверяемое поведение; предпосылки можно реализовать минимально
и расширять после эксперимента.

### A. Проверочные задачи и стартовый профиль

**Риск:** построить убедительное демо, не соответствующее работе замерщика.

**Работа:** собрать с практиком несколько типичных планов и пожеланий.
Для каждого записать исходные данные, обязательное/предпочтения/неизвестное,
допустимые компромиссы и признаки приемлемого результата. Отдельно добавить
синтетические граничные случаи, не выдавая их за реальные интервью.

**Технический результат:** serializable fixtures и небольшой экспериментальный
профиль каталога. Должна проверяться семантика результата, не совпадение с одной
идеальной картинкой, когда правильных решений несколько.

**Проверка:** задача воспроизводится без браузера; понятны причины успеха/отказа.
Недостаток реальных кейсов не блокирует технический прототип, но его правила
и выводы о ценности помечаются неподтверждёнными.

### B. Первая прямая кухня end-to-end

**Риск:** несовместимость желаемого генератора с текущим редактором/сохранением.

**Минимальная реализация:**

- Один выбранный ряд и небольшой набор совместимых семейств.
- Форма требований плюс сводка критичных условий; не заставлять заранее
  поставить каждый прибор, если размещение поручено генератору.
- Ограниченный поиск, typed diagnostics, preview, принятие, Undo и reload.
- Одна ручная фиксация и один локальный запрос изменения.
- Маленький экспериментальный диалог через тот же контракт; можно начать
  с детерминированного mock-адаптера, затем проверить живую модель.
- Простая диагностика длительности, отказов и числа исправлений.

**Готовность:** принятый эскиз редактируется обычными инструментами; ошибочный
или поздний ответ ничего не портит; подтверждённые данные сохраняются.

**Чего пока не нужно:** полный каталог/дизайн-система, универсальный язык шаблонов,
облако проектов, сложный поиск для всех комнат.
Если выявилась необходимость небольшой части среза C, сделать её для прототипа,
а не ждать окончания всего каталога.

### C. Семейства, оформление и пригодность установки

**Риск:** UI меняет внешность, но геометрия, правила и сохранение расходятся.

**Работа:** вынести минимальные общие определения из UI-каталога; добавить
конфигурации фасадов, явную роль/опоры, размерную политику и совместимый legacy-путь.
Из той же конфигурации строить 2D/фасад/3D, крепления ручек и зоны проверки.

Ручки задаются моделью и смысловым положением относительно секции.
Локальные координаты выводятся из секции, а не хранятся как случайные смещения.
Варианты ящиков учитывают занятую техникой область; прямое добавление нового mesh
не считается завершённой поддержкой модуля.

**Проверка:** типовой/нестандартный размер, поворот, угол, окно, встроенная техника,
изменение конфигурации, Undo и JSON round-trip. Старые проекты открываются без
необъяснимой замены фасадов. Общий стиль сохраняет индивидуальные исключения.

**Условие пересмотра:** если необходим произвольный конструктор деталей,
вернуться к границе MVP; не строить скрытый производственный CAD.

## 9. Срез D: адаптивные решения и сравнение

**Риск:** прямой ряд работает, но угол/нехватка места/ручные правки ломают решение.

Расширить поиск до согласованных прямой и Г-образной схем, функциональных
фрагментов, гибридных размеров, доборов и явных пользовательских фиксаций.
Добавить частичную перестройку и объяснимое сравнение.

Кандидаты краткоживущие; понравившееся решение можно сохранить как именованный
вариант. Первая реализация может использовать существующий duplicate проекта:
независимые документы с опциональной группировкой и ссылкой на происхождение.
Не переиспользовать autoCountertop.groupId как идентификатор группы вариантов.

Внутренние object IDs при копировании можно сохранять для сопоставления,
если внешнее обращение всегда содержит projectId и тип объекта.
Изменение комнаты в копии не меняет исходный вариант. Shared room, merge,
синхронное редактирование всех вариантов — вне начальной модели.

**Проверка:** один/несколько/ноль вариантов; перестановка семантически неупорядоченных
входных наборов не меняет расчёт; небольшая правка не перестраивает всё; копия переживает reload
и не влияет на оригинал. Пользователь понимает отличие «ещё кандидат»,
«принять» и «сохранить как вариант».

**Пересмотр:** при взрыве перебора профилировать реальные случаи.
Сначала ограничить поддерживаемое пространство/улучшить pruning; Worker либо
серверный solver добавлять по измерениям, не ради модного инструмента.

## 10. Срез E: рабочий ИИ-планировщик

**Риск:** неопределённый язык превращается в неконтролируемые изменения.

### Контракт агента

Агент получает компактный снимок: доступные роли/конфигурации, требования,
объектные ссылки, область изменений, фиксации и необходимые проверки.
Не отправлять полный renderer, произвольные ресурсы и лишние данные клиента.

Начать с малого набора действий: изменить требование, выбрать шаблон/стиль,
предложить генерацию области, заменить конфигурацию, объяснить конфликт.
Измеренные координаты и исправления применяются ядром по подтверждённому предложению.
Устройство чата, выбор поставщика модели и схема API пока не фиксированы.

Содержимое диалога и внешние описания — данные, не разрешение выполнить код,
скачать URL или обойти ограничения. Разрешённые family/config IDs проверяются.
Структурированный JSON проверяет формат, но не физическую корректность.

### Сервер и устойчивость

Минимальный backend обеспечивает секреты доступа к модели, ограничения запросов,
таймауты, отмену и диагностические коды. Python допустим, не обязателен;
не заводить PostgreSQL и облачные аккаунты проектов только ради одного API-вызова.
Доступ к платному endpoint ограничивается подходящим пилоту механизмом
аутентификации/квот, а не открытым прокси с общим ключом.

Ограничить число попыток самокоррекции, длительность и размер контекста.
При ошибке показать понятное состояние и сохранить ручную альтернативу.
Ответы модели, ошибки и тексты входа не попадают бесконтрольно в аналитику.

**Проверка:** fake provider в обычных тестах; отдельный opt-in корпус живых
запросов с версиями prompts/model/config. Проверять извлечённое намерение
и итоговые ограничения, не буквальное совпадение текста.
Удачный пример с одной моделью не считается доказательством надёжности агента.

**Готовность:** генерация и локальные диалоговые изменения проходят через один
безопасный механизм с формой; неизвестный ID/конфликт/сеть/поздний ответ не повреждают проект.

## 11. Сквозная работа: версии, сохранение и миграции

Не откладывать до последнего этапа. Каждое новое значимое поле проходит цепочку:

1. Zod-схема и доменная семантика.
2. Миграция старого формата с сохранением оригинала при ошибке.
3. Сериализация/partialize и загрузка.
4. История, включая snapshot/comparison и политику Undo.
5. Подписка ProjectSession на изменение данных.
6. Duplicate, JSON export/import и восстановление текущего проекта.
7. Проверки ссылок и совместимости после восстановления.

Различать версии: структуры документа, envelope резервной копии, схемы IndexedDB,
каталога/правил/шаблонов и ревизию текущих изменений.
Они решают разные задачи и не должны быть одним счётчиком.

Поля с безопасным default помогают, но не заменяют семантическую миграцию.
Не округлять старые нестандартные размеры под новую сетку при открытии.
Не регенерировать расстановку из одного templateId: сохраняется принятая кухня
с фактическими параметрами и достаточными сведениями о её происхождении.

Если определение каталога недоступно, открывать сохранённый результат в понятном
совместимом/ограниченном режиме либо явно сообщать невозможность восстановления.
Не подменять молча похожим шкафом. Полная система discontinued replacements не нужна.

Метаданные группы вариантов на уровне ProjectRecord не входят автоматически
в JSON документа. Явно решить, переносится ли связь при импорте, и не связывать
импорт с чужим существующим проектом по одному недоверенному ID.
Неизвестная будущая версия не должна перезаписывать рабочее сохранение.

## 12. Срез F: передача эскиза и проверка на объекте

### Список модулей

Вычисляется из принятого снимка отдельной чистой функцией/селектором:
тип/семейство, конфигурация, размеры, количество, нестандартность,
замечания и ссылки на реальные объекты. UI-номер не используется как ID.
Источник — документ, не обход Three meshes.

Разделять самостоятельные шкафы/технику и производные сборки.
L-столешница может иметь несколько частей с groupId: показать сборку и её части,
не выдавать число геометрических секций за число товарных столешниц.
У несвязанных прямых элементов без assembly ID не угадывать объединение по цвету.
Ручки/фасады не становятся точной закупочной спецификацией, пока нет достаточных данных.

### Пакет результата

Один согласованный snapshot/revision даёт 3D-вид, план/нужные фасады,
основные размеры, список модулей и неразрешённые условия.
Если проект изменился за время подготовки, не смешивать новый список со старым кадром.
Показывать имя варианта, дату/версию и назначение «предварительный эскиз».

Начать с локального просмотра/печати или простого файла, формат определить по
получателю. PDF backend, публичные ссылки и CRM не обязательны.
Ошибка экспорта не мешает сохранить проект; тяжёлый экспорт не запускается
каждые несколько сотен миллисекунд вместе с autosave.

### Планшет, сеть, наблюдаемость

Проверить реальные размеры экрана, touch/долгое нажатие, выбор наложенных объектов,
клавиатуру числовых полей и возврат между видами. Режим показа клиенту — возможное
упрощение UI, не отдельная система ролей.

Офлайн-запуск требует кэша приложения/ресурсов и проверки обновлений.
IndexedDB не гарантирует ни запуска без сети, ни вечного хранения в браузере.
Проверять перезагрузку без сети, ошибку записи/квоту и понятный экспорт резервной копии.
ИИ недоступен без сети, но ручная работа и доступный локальный генератор остаются.

Минимальный журнал со сквозного прототипа: начало/исход поиска, просмотр/принятие/
отклонение, ручная правка после генерации, экспорт и повторное открытие.
События привязывать к запросу/ревизии без утечки адресов, телефонов и полного диалога.
Внешняя telemetry-платформа не обязательна; локальных измерений для начала достаточно.

**Готовность:** замерщик завершает целевой сценарий без разработчика, получатель
понимает пакет, измерены время и объём исправлений. Это критерий опыта пилота,
не доказательство рынка или совместимости со всеми фабриками.

## 13. Проверки и регрессионный корпус

| Уровень         | Что проверять                                                                                           |
| --------------- | ------------------------------------------------------------------------------------------------------- |
| Unit: каталог   | Допустимые конфигурации/размеры, вычисление секций и ручек, legacy-совместимость                        |
| Unit: правила   | ID/ссылки, стены/проёмы/опоры, открывание, unknown отдельно от hard/soft                                |
| Unit: генератор | Фиксации, сумма ряда, доборы, границы размеров, детерминизм и честные статусы поиска                    |
| Integration     | Preview без записи, apply одним Undo, производные сборки, stale/duplicate/cancel и переключение проекта |
| Persistence     | Миграции, reload, JSON round-trip, копии вариантов, недоступный каталог                                 |
| UI/E2E          | Сводка условий, изменение через форму/агента, выбор кандидата, переход к ошибке, экспорт                |
| Пилот           | Скорость, ручные исправления, удобство планшета, доверие к предупреждениям                              |

Сценарии по известным проблемам сложных планировщиков:

- Длина/толщина/удаление стены после размещения, добавление окна и перегородки.
- Положение мебели не зависит от поворота камеры; навесной блок сохраняет высоту.
- Resize базы пересчитывает фасады, доборы и столешницу без промежуточного рассогласования.
- Врезка/фиксации/замечания пользователя сохраняются после reload.
- Частичная генерация не меняет внешние объекты, кроме явно показанных зависимых сборок.
- Поздний ответ после Undo, смены проекта или ручной правки не применяется.
- Ошибочная обязательная ссылка и отсутствующая техника не скрываются нормализацией.
- Один допустимый кандидат не клонируется ради «трёх вариантов».
- Недоступный каталог/неизвестная версия не приводит к потере старого эскиза.

Полезные свойства для property-based или параметризованных тестов: неизменность входа,
сохранение locks, независимость от порядка неупорядоченных по смыслу наборов,
стабильная повторная нормализация,
согласованность преобразования локальных координат и отсутствие новых hard-конфликтов.
Это не распространяется на последовательности с геометрическим смыслом: порядок
room.walls сейчас участвует в распознавании контура; перестановка его элементов
не обязана сохранять план. Не менять топологическую модель ради общего тестового лозунга.
Вводить генерацию тестовых данных постепенно; библиотека не обязательна.

Проверять семантику, а не только snapshot сериализованного массива и не только screenshots.
Скриншоты нужны для фасадов/ручек/стыков, но не доказывают корректность ограничений.
Новый пакет не добавляется только ради проверки, которую можно выразить существующим Vitest.

## 14. Как менять этот план и продолжать работу

### Перед каждой задачей

1. Уточнить ограниченный пользовательский результат и актуальное состояние репозитория.
2. Выбрать минимальный срез и наиболее рискованное предположение.
3. Найти существующие точки расширения; проверить изменения пользователя.
4. Сформулировать проверку успеха и путь совместимости.
5. Реализовать только нужную часть, не весь раздел «заодно».

### Когда пересматривать решение

- Реальные кейсы не покрываются выбранным шаблоном/каталогом.
- Стоимость/задержка поиска или ИИ нарушает сценарий на объекте.
- Новая абстракция сложнее ограниченного специального алгоритма.
- Правило конфликтует с практикой мебельщика или границей ответственности.
- Пользовательское тестирование показывает, что форма удобнее диалога.
- Существующая модель данных не сохраняет смысл правок/вариантов.

Фиксировать кратко: **что предполагали → что обнаружили → что меняем →
какие данные/сценарии затронуты → чем проверяем**.
Значимое реализованное архитектурное решение переносить в architecture-decisions;
текущие механизмы — в ARCHITECTURE; изменение обещаний — в product.
Не переписывать историю исследования, будто новый вывод был известен изначально.

### Открытые решения

| Вопрос                        | Рабочее направление                           | Что нужно для выбора                                |
| ----------------------------- | --------------------------------------------- | --------------------------------------------------- |
| Точные размеры и конфигурации | Один экспериментальный профиль                | Кейсы и проверка мебельщиком                        |
| Фиксация пристенного объекта  | Явная система координат lock                  | Сценарий изменения стены                            |
| Каталог в старом проекте      | Версия + сохранённая разрешённая конфигурация | Прототип миграции/удаления позиции                  |
| Вид предложения               | Полный candidate или ограниченный patch       | Простота атомарного apply и diff                    |
| Иерархия вариантов            | Независимые копии сначала                     | Потребность в группировке на пилоте                 |
| Solver/Worker/server          | Простой локальный поиск                       | Профилирование граничных задач                      |
| ИИ-провайдер/backend          | Малый typed API, ключ на сервере              | Качество, стоимость, доступность и обработка данных |
| Формат передачи               | Снимок + производный список                   | Реальный получатель эскиза                          |

### Ближайший рекомендуемый срез

Первый прямой ряд, короткая форма, чистая генерация, preview и атомарное принятие
уже реализованы в ограниченном виде. Следующий эксперимент — одна ручная фиксация
модуля и локальное изменение предложения (например, «добавь рабочую поверхность»)
через тот же проверяемый контракт. Затем сравнить короткую форму с маленьким
диалогом, не давая модели права писать координаты прямо в проект. Параллельно
проверить несколько реальных кейсов замерщика и уточнить правила установки техники.

Это рекомендация по снижению риска, не запрет начать с конкретного модуля,
валидации или миграции, если актуальная задача обоснованно требует этого.
После каждого среза отмечать: что реально работает, какие проверки выполнены,
какие гипотезы остались и какой следующий эксперимент полезнее всего.
