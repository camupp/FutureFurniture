# Архитектура

Документ описывает устройство кода и предназначен в первую очередь как контекст
для ИИ-ассистента: здесь зафиксированы соглашения, системы координат, инварианты и причины
неочевидных решений. Продуктовое описание — в [product.md](product.md).

---

## 1. Границы работ

**Итерация 1:** 2D-план (стены) → параметрический блок → 3D-визуализация, вид спереди,
панель свойств, проверка выхода за контур, экспорт кадра, сохранение в localStorage.

**Итерация 2 (расстановка):** каталог из шести пресетов, геометрии столешницы, мойки и
плиты, привязка блока к стене с автоповоротом, стыковка однотипных блоков вплотную,
вытеснение из пересечений, притяжение по высоте и врезание техники в столешницу.

**Итерация 3 (обмер помещения):** окна и двери с привязкой к стенам, инженерные выводы,
редактирование и отображение этих объектов в плане, фасаде и 3D, вырезы в геометрии стен,
проверка перекрытия мебелью, пинч-зум на планшете.

**Итерация 4 (стенные ряды):** явная привязка мебели к стене, локальная координата вдоль
стены, отдельный фасад выбранной стены, перенос мебели вместе с изменённой стеной и
миграция старых сохранений.

**Итерация 5 (автостолешницы):** построение столешницы по непрерывному ряду напольных
тумб одной стены, автоматический пересчёт зависимой геометрии и переход к ручной правке.

**Сознательно отложено:** Dexie/IndexedDB и список проектов, PWA-обвязка, бэкенд, LLM.

Причина: сначала проверяется сквозной путь «нарисовал → расставил → показал клиенту».
Всё остальное наращивается поверх без переписывания существующих модулей.

## 2. Ключевые соглашения

1. **Все линейные размеры в модели — миллиметры, целые.** Перевод в метры (`mmToM`)
   происходит только на границе с Three.js. В Konva миллиметры рисуются напрямую:
   масштаб задаётся трансформом Stage.
2. **2D-план — источник истины для геометрии, 3D — производная.** В 3D нет собственного
   состояния объектов, только чтение стора.
3. **Вся логика на клиенте.** Сетевых вызовов нет вообще.
4. **Доступ к данным только через стор.** Компоненты не читают и не пишут localStorage
   напрямую — это оставляет возможность заменить persist-слой на Dexie без правок в UI.

## 3. Системы координат

Самое частое место ошибок, поэтому разбор подробный.

### План (RoomEditor, Konva)

- `x` — вправо, `y` — **вниз** (как в экранных координатах Konva). Единицы — мм.
- Угол стены: `wallAngle = atan2(dy, dx)`, радианы.
- Поворот блока `rotation` — градусы, положительное значение = по часовой стрелке на экране.
  Konva-свойство `rotation` совпадает с этим напрямую, ничего конвертировать не нужно.
- Матрица поворота в `rotatePoint` — обычная математическая; в системе с осью y вниз она
  визуально даёт вращение по часовой стрелке. `itemFootprint` и Konva согласованы.

### Фасад стены (ElevationEditor, Konva)

- По горизонтали — локальная ось выбранной стены (мм). Ноль находится слева для
  наблюдателя внутри комнаты: для стороны `right` шкала разворачивается функциями
  `wallOffsetToDisplay` / `displayToWallOffset`.
- По вертикали — высота над полом, но Konva рисует вниз, поэтому **высота `h` лежит на
  координате `y = -h`**. Пол — линия `y = 0`, потолок — `y = -wallHeight`.
- Группа блока позиционируется в `(displayOffset, -item.elevation)`, а прямоугольник
  внутри рисуется от `y = -height` до `y = 0`. То есть локальный ноль группы — низ блока.

### 3D (Three.js)

- Метры. Отображение плана в мир: **`plan.x → world.X`, `plan.y → world.Z`**,
  высота — `world.Y`, пол на `Y = 0`.
- Поворот вокруг вертикали: **`rotation.y = -θ`**, где `θ` — угол из плана в радианах.
  Вывод: `rotation.y = φ` переводит `(1,0,0)` в `(cos φ, 0, -sin φ)`; нужно
  `(cos θ, 0, sin θ)`, следовательно `φ = -θ`. Это касается и стен (`-wallAngle`),
  и блоков (`-degToRad(item.rotation)`).
- Пол строится из `THREE.Shape` по точкам плана и поворачивается на `+π/2` вокруг X
  (именно `+`, иначе план отражается по оси Z), материал — `DoubleSide`, и опущен на
  `y = -0.002`, чтобы не конфликтовать с нижними гранями стен.

## 4. Модель данных (`src/shared/types.ts`)

Типы выводятся из Zod-схем (`z.infer`), то есть схема — единственный источник правды.

```ts
Point   = { x, y }                                   // мм, координаты плана
Wall    = { id, start: Point, end: Point, thickness } // толщина 50–500 мм
Opening = { id, wallId, type, offset, width, height, sill, hinge }
Utility = { id, type, point: Point, height, mount: WallMount | FloorMount }
Room    = { walls, wallHeight, openings, utilities }

BlockType   = 'cabinet' | 'countertop' | 'sink' | 'hob'
BlockParams = { width, height, depth, facadeColor }
FurnitureItem = {
  id, type: BlockType,
  position: Point,   // центр блока на плане
  elevation: number, // низ блока над полом: 0 — напольный, 1400 — навесной
  rotation: number,  // градусы по часовой; 0 — фасад смотрит в +y
  params: BlockParams,
  wallAnchor?: { wallId, side: 'left'|'right', offset, distance },
}
```

**Все блоки — это параметрический ящик `width × height × depth`**, поставленный в точку
`(position, elevation)` и повёрнутый на `rotation`. `type` меняет только геометрию внутри
ящика и дефолтные габариты. Благодаря этому вид сверху, вид спереди, валидация и привязки
написаны один раз и не знают про типы блоков. Для столешницы `height` — это толщина плиты.

Границы значений вынесены в `WALL_LIMITS`, `ELEVATION_LIMITS` и `BLOCK_LIMITS` (последний —
свой набор на каждый тип блока). Они используются **одновременно** в полях ввода и при
ограничении значений в сторе. Zod-схема параметров намеренно шире границ: её задача —
отсеять мусор из хранилища, а не дублировать продуктовые ограничения.

`BUILT_IN_TYPES` (мойка, плита) — встраиваемая техника, которая по определению
находится внутри других блоков и потому исключена из проверки пересечений.

`elevation` объявлен как `.default(0)`: это даёт обратную совместимость с проектами,
сохранёнными до появления высоты установки. **При добавлении новых полей в схему
используйте `.default(...)`, иначе `merge` при загрузке отбракует весь сохранённый проект.**

### Инварианты

- Стены — **цепочка**: `walls[i].end` совпадает с `walls[i+1].start`. Контур помещения
  (`roomPolygon`) строится как `[walls[0].start, ...walls.map(w => w.end)]`, а дубль
  последней точки отбрасывается, если контур замкнут. Отдельно стоящая стена ломает
  корректность контура — это известное ограничение модели.
- Центр габаритного прямоугольника блока (`bounds(itemFootprint(item)).center`) всегда
  равен `item.position` — блок вращается вокруг собственного центра. На этом построена
  логика перетаскивания в виде спереди.
- Проём принадлежит стене по `wallId`, а `offset` — расстояние от начала стены до центра
  проёма. `normalizeOpening` удерживает его целиком внутри стены и ниже потолка; у двери
  `sill` всегда равен нулю. Стену нельзя укоротить сильнее ширины принадлежащего ей проёма.
- Инженерный вывод имеет `mount`: `{ kind: 'wall', wallId, offset }` или
  `{ kind: 'floor' }`. Для стены мировая точка и ориентация вычисляются через
  `utilityPoint`/`wallUtilityFrame`, поэтому вывод следует за стеной и выступает внутрь
  помещения. Напольный вывод хранит свободную точку плана и всегда начинается с Z = 0.
- Мебель может иметь `wallAnchor`. `offset` — координата центра вдоль стены, `side` —
  её стабильная грань, `distance` — зазор до задней грани мебели. Пока привязка существует,
  `position` и `rotation` синхронизируются из неё через `furnitureFromWallAnchor`. Свободная
  мебель и острова `wallAnchor` не имеют.

## 5. Стор (`src/shared/store.ts`)

Один Zustand-стор со всем состоянием приложения.

**Данные:** `room` (`walls`, `openings`, `utilities`), `furniture`.
**UI-состояние:** `selection` (`{kind: 'wall'|'opening'|'utility'|'furniture', id}` или
`null`), `tool` (`select | wall | window | door | utility | pan`), `orthoSnap`,
`utilityType`, `smartPlacement`, `viewMode` (`2d | split | 3d`), `editorView`
(`plan | elevation`), `elevationWallId`.

**Действия:** `addWall`, `updateWallLength`, `updateWallThickness`, `removeWall`,
`setWallHeight`, `clearRoom`, CRUD для проёмов и выводов, `addBlock`, `moveFurniture`, `dropFurniture`,
`moveFurnitureAlongWall`, `detachFurniture`, `dropInSection`, `elevateFurniture`, `rotateFurniture`, `updateFurnitureParams`,
`addCountertopForRow`, `detachCountertop`, `removeFurniture`, плюс сеттеры UI.

**Точное перемещение и перетаскивание разведены намеренно.** У свободного блока
`moveFurniture` ставит X / Y ровно и снимает прежнюю привязку; у пристенного
`moveFurnitureAlongWall` точно меняет `offset`, не отрывая от стены. `elevateFurniture`
точно задаёт Z. `dropFurniture` и `dropInSection` вызываются только при перетаскивании
и прогоняют координаты через магниты. Если их объединить, ручной ввод чисел начнёт
«прилипать» к соседям и станет неуправляемым.

**Селекторы:** `selectedFurniture`, `selectedWall`, `selectedOpening`, `selectedUtility` — используются как
`useAppStore(selectedFurniture)`.

**Ограничение значений живёт в сторе, а не в компонентах.** `updateFurnitureParams`
зажимает габариты по `BLOCK_LIMITS`, `elevateFurniture` — по
`[0, wallHeight − высота блока]`, `rotateFurniture` нормализует угол в `[0, 360)`.
Любой новый ввод можно слать в стор «как есть».

### Сохранение

`persist` с ключом `future-furniture-project`. `partialize` сохраняет только
`room`, `furniture`, `viewMode`, `elevationWallId` — инструменты и выделение при перезагрузке сбрасываются
намеренно. В `merge` сохранённые данные прогоняются через `projectSchema.safeParse`,
и при ошибке берётся состояние по умолчанию: битый localStorage не должен вешать
приложение. Новые массивы `openings` и `utilities` имеют `.default([])`, а после загрузки
проёмы и выводы нормализуются относительно актуальных стен. Старый вывод без `mount`
получает `{ kind: 'floor' }`, поэтому сохранения предыдущей схемы продолжают загружаться.
Старая мебель без `wallAnchor` получает привязку только если она однозначно совпадает
с одной стеной по положению задней грани и углу; остальные блоки остаются свободными.
Метаданные `autoCountertop` сохраняются вместе с мебелью, а производные размеры и
координаты столешницы после загрузки вычисляются заново по актуальным опорам.

Проект по умолчанию — прямоугольник 3600 × 3000 мм, стены 100 мм, высота 2700 мм,
чтобы приложение не открывалось пустым холстом.

### `useStageViewport`

Оба 2D-холста используют один хук: состояние `{scale, x, y}`, `fitTo(points)`,
`zoomBy(factor)`, обработчики колеса, перетаскивания и касаний. Трансформ вешается на сам `Stage`,
поэтому указатель в миллиметрах берётся функцией `stagePointer(stage)` через
`stage.x() / stage.scaleX()` — так значения корректны и во время перетаскивания холста,
когда позиция Stage меняется мимо React-состояния.

Диапазон масштаба — `0.005…1` px/мм. Толщина линий, размеры подписей и радиусы вершин
компенсируются вручную: `strokeScaleEnabled={false}` для линий и `scaleX/Y = 1/scale`
для `Label`, иначе они масштабируются вместе со сценой.

Пинч-зум хранит предыдущие расстояние и центр между двумя касаниями. Масштаб меняется
вокруг этой точки, а активный drag Stage останавливается, чтобы холст не уезжал за первым
пальцем.

### RoomEditor

- Инструменты: `select` (выделение и перетаскивание объектов), `wall` (рисование цепочки
  стен), `window`/`door` (проём кликом по ближайшей стене), `utility` (инженерный вывод),
  `pan` (панорама холста).
- В режиме `select` ПКМ или долгое нажатие 550 мс открывает контекстное меню. На стене
  доступны окно, дверь и настенные выводы; на полу — канализация, вода и розетка.
  Долгое нажатие отменяется при движении пальца более чем на 10 px, чтобы не мешать
  панораме и щипку.
- Привязки при рисовании: сначала к существующей вершине (радиус 14 px в экранных
  единицах, то есть `14 / scale` мм), иначе — ортогональная привязка к предыдущей точке
  при включённом «Углы 90°», затем округление к сетке 10 мм.
- Цепочка завершается по Esc, двойному клику или кликом в первую вершину контура.
- `setWallLength` двигает конец стены вдоль её направления и **сдвигает все последующие
  стены цепочки на ту же дельту**, чтобы контур не разорвался.
- Окно, дверь и настенный вывод двигаются только вдоль своей стены. Обозначение двери
  открывается внутрь контура и учитывает сторону петель; напольные выводы свободно
  двигаются по сетке 10 мм. При удалении стены удаляются принадлежащие ей проёмы и выводы.
- Во время перетаскивания мебели целевая стена подсвечивается зелёным. После отпускания
  сохраняется `wallAnchor`; при изменении длины или толщины стены привязанные блоки
  пересчитывают мировые координаты. Удаление стены отвязывает мебель, сохраняя её место.

### ElevationEditor — «Фасад стены»

- Редактор показывает только объекты стены `elevationWallId`; соседние стены переключаются
  стрелками. Для мебели дополнительно должна совпадать внутренняя сторона стены.
- По горизонтали используется `wallAnchor.offset`, поэтому ширина блока на фасаде всегда
  равна `params.width` и не зависит от направления стены на плане.
- Вертикальное перетаскивание ограничено `dragBoundFunc` в экранных координатах:
  `y ∈ [view.y − (wallHeight − height) · scale, view.y]`, то есть блок не проваливается
  под пол и не уходит в потолок.
- Один drag меняет сразу `wallAnchor.offset` и `elevation`. `placeBlockInSection` удерживает
  блок на выбранной стене, применяет защитные зоны и соседей, а по вертикали вызывает
  `snapElevation`. Магнит работает вживую, как на плане.
- Проёмы и настенные выводы отображаются только для выбранной стены. Напольные выводы
  видны на фасаде, если находятся не дальше 1000 мм перед ней; их высота остаётся нулевой.

### Scene3D

- Посадка камеры (`CameraFit`) выполняется при монтировании и по кнопке
  «Сбросить камеру». Радиус описанной сферы помещения делится на `sin(fov/2)` и на
  `min(1, aspect)` — деление на aspect нужно, чтобы комната влезала и в узкой панели.
- **Эффект посадки камеры не запускается, пока канвас нулевого размера** (`hasSize`):
  при `aspect = 0` расстояние обращается в бесконечность и сцена выглядит пустой.
- `OrbitControls` с `maxPolarAngle = π/2 − 0.05`: камера не опускается ниже горизонта.
- Стена, оказавшаяся между камерой и центром комнаты, плавно уходит в прозрачность
  (`FADED_OPACITY = 0.1`). Сторона определяется знаком скалярного произведения наружной
  нормали стены и вектора «центр стены → камера», пересчёт в `useFrame` с интерполяцией.
  `depthWrite` выключается у прозрачных стен, иначе они перекрывают мебель.
- Свет: ambient + hemisphere + направленный с тенями (`shadow-camera` ±10 м).
- Экспорт кадра: `gl.domElement` кладётся в модульный ref (`screenshot.ts`), у канваса
  включён `preserveDrawingBuffer: true` — без него `toDataURL()` вернул бы пустой кадр.

Стена с проёмами не строится одним `ExtrudeGeometry`: отверстие двери касается нижней
границы контура, а пересекающиеся отверстия делают триангуляцию `Shape.holes`
неустойчивой. `panelSegments` разбивает панель по границам всех проёмов и возвращает
набор прямоугольных секций стены. Окно дополняется рамой, стеклом и подоконником, дверь —
трёхсторонней коробкой и полотном. Проёмы и инженерные выводы можно выбрать прямо в 3D.
Выводы имеют геометрию по типу (пара труб горячей/холодной воды, канализационная
труба, клапан, решётка или розетка). Настенная геометрия ориентируется по внутренней
нормали стены, напольная растёт вертикально; зелёная обводка означает совместимую сборку.

### Cabinet — параметрическая геометрия

Локальный ноль: центр по ширине, низ блока на `y = 0`, фасад смотрит в `+z`.

Раскладка по глубине `d`: корпус занимает `[-d/2, -d/2 + bodyDepth]`, фасад —
оставшиеся 18 мм до `+d/2`. Число дверей: 2 при ширине > 600 мм, иначе 1; ширина двери
считается с зазором 3 мм. Ручка — брусок 128 мм у открывающегося края.

Цоколь высотой 100 мм существует только при `onFloor` (то есть `elevation === 0`):
поднятый блок трактуется как навесной и цоколя не имеет. Глубина цоколя —
`depth − 50 мм`, то есть его перед утоплен под фасад на 50 мм. Цвет — цвет фасада,
затемнённый до 72%. Ручка у напольного блока стоит вверху дверцы, у навесного — внизу:
до навесного шкафа надо дотянуться.

### Врезная техника и вырезы в столешнице

Мойка и плита опираются на столешницу только верхней частью — бортиком у мойки и
стеклянной плитой у варочной панели, остальное уходит вниз. Толщина этой опорной части
живёт в `BUILT_IN_FLANGE` (`shared/types.ts`) и используется в трёх местах: в геометрии
блока, в дефолтах каталога и в притяжении по высоте. Отсюда формула отметки:
`elevation = верх_столешницы − (высота_блока − толщина_бортика)`.

Чтобы корпус не пересекал плиту, `Countertop` строится не боксом, а `ExtrudeGeometry`
из `THREE.Shape` с дырками: `FurnitureMesh` считает вырезы под каждую встраиваемую
технику, лежащую в границах этой плиты, переводя её габариты в локальную систему
столешницы. Вырез на 35 мм уже блока с каждой стороны — на эту кромку и опирается бортик.

**Бортик мойки — рамка, а не плита.** Сплошной прямоугольник сверху закрывал бы чашу, и
мойка выглядела бы плоской заглушкой. Бортик строится тем же приёмом, что и столешница:
`ExtrudeGeometry` с отверстием по внутреннему контуру чаши. Сама чаша собрана из дна и
четырёх стенок — открытая сверху.

**Корпус тумбы — тоже призма с вырезами, а не коробка.** Мойка стоит внутри тумбы, и
верхняя грань обычного `boxGeometry` перекрывала бы чашу: сверху было видно светлую
крышку корпуса вместо тёмного дна. Поэтому корпус строится тем же `buildSlab`, только
толщиной во всю высоту — получается сквозная шахта под врезной блок. Общий помощник —
`parametric-blocks/slab.ts`, им пользуются столешница и корпус шкафа.

Материал внутренностей чаши заметно темнее и матовее бортика: горизонтальное дно ловит
почти весь свет, и при металличности бортика цвет выбивало в белый.

Совпадающие плоскости недопустимы: они дают мерцание (z-fighting). Поэтому врезной блок
встаёт на 2 мм выше верха столешницы (`FLUSH_GAP`), а стенки чаши заходят в бортик
с перекрытием.

### Притяжение по высоте (`shared/utils/elevation.ts`)

Вертикальный аналог привязок на плане. `snapElevation` собирает осмысленные отметки для
блока и притягивает к ближайшей в пределах 200 мм:

- врезной блок (мойка, плита) — заподлицо со **столешницей**, под которой он оказался;
- обычный блок — на верх того, над чем он стоит (столешница садится на тумбы);
- пол.

Врезной блок намеренно **не** притягивается к голой тумбе: без столешницы мойка должна
висеть на той же отметке, как если бы столешница была на месте, но прозрачной.

Притяжение применяется в `dropFurniture` (перетащил на виде сверху — встало по высоте) и в
`dropInSection` (перетаскивание на виде спереди) и отключается той же галочкой
«Умная расстановка». У свободного блока поля X / Y / Z меняют координаты точно; у
пристенного вместо X / Y редактируется локальное смещение, ограниченное свободным
отрезком стены.

### Тени

У направленного света обязательны `shadow-bias` и `shadow-normalBias`: без них тонкие
плиты — столешница и стеклянная панель — покрываются полосами самозатенения
(shadow acne), которые легко принять за мерцание текстур.

### Привязки (`shared/utils/snapping.ts`)

`placeBlock` считается **на каждый кадр перетаскивания**, а не только при отпускании:
блок притягивается прямо под курсором, как в кухонных планировщиках, и не прыгает в конце
жеста. `FurnitureShape` в `onDragMove` прогоняет позицию узла через `placeBlock` и тут же
записывает результат в узел Konva, а в `onDragEnd` отдаёт ту же точку в стор.

Порядок шагов важен:

1. **Стена.** Ищется ближайшая стена в радиусе `глубина/2 + 350 мм` от центра блока. Блок
   разворачивается так, чтобы фасад смотрел по внутренней нормали стены
   (`rotation = atan2(-nx, ny)`), и ставится задней гранью вплотную к внутренней грани
   стены — смещение `толщина_стены/2 + глубина_блока/2`. Положение вдоль стены зажимается
   не по осевым концам, а по свободному внутреннему отрезку: тела примыкающих стен
   пересекаются с полосой глубины мебели в локальных координатах. Поэтому блок не входит
   в толщину соседней стены также при неравной толщине и косом угле.
   Результат содержит `wallAnchor`; это не временный эффект отрисовки, а часть проекта.
2. **Сосед.** Позиция переводится в локальную систему соседа (`rotatePoint` на `-rotation`
   соседа). Если углы совпадают с точностью до 1° (или отличаются на 180°), смещение вдоль
   глубины меньше полуглубины, а зазор вдоль ширины отличается от точки касания менее чем
   на 200 мм — блок ставится ровно в касание.

3. **Вытеснение от мебели.** Если после привязки блок всё-таки пересекается с другим, он съезжает
   вдоль собственной ширины к ближайшему краю помехи и встаёт вплотную — до восьми шагов,
   чтобы разрулить цепочку. Это ключевая механика расстановки: блок бросают примерно
   в нужное место, а он сам встаёт в ближайшее свободное, вместо того чтобы залезать
   на соседа и подсвечиваться красным. Без неё размер приходилось подгонять вручную
   по пикселю или через поля координат.
4. **Защитные зоны проёмов.** Вдоль окна и дверного проёма оставляется запас 100 мм.
   Для двери дополнительно строится сектор движения полотна с запасом 120 мм. Если
   высоты блока и проёма пересекаются, блок сдвигается вдоль своего ряда за ближайшую
   границу запретной области. Тумба ниже подоконника этому правилу не мешает.

Стыкуются **только однотипные блоки одного ряда**: совпадает тип и высота установки
(допуск 50 мм). Столешница должна ложиться поверх тумб, а не вставать с ними в один ряд,
а навесной шкаф — висеть над тумбой, а не рядом с ней. Без фильтра по типу столешница
2400 мм «примагничивалась» торцом к шкафу и уезжала за пределы комнаты; без фильтра по
высоте навесной шкаф забирал глубину напольной тумбы и отходил от стены на её переднюю
кромку.

Если блок был посажен на стену, после стыковки и выталкивания он возвращается на её линию
(`keepOnWall`): эти шаги двигают блок свободно и могут оторвать его от стены. Сохраняется
смещение вдоль стены, восстанавливается поперёк.

При изменении ширины или глубины пристенного блока `updateFurnitureParams` повторяет
посадку через `placeBlockOnWall`: сохраняет конкретную стену и сторону, обновляет отступ
по глубине, зажимает новый размер в углах и при включённой умной расстановке освобождает
пересечение с соседом или проёмом. Цвет и высота не запускают горизонтальную перестановку.

Подписи плана прореживаются попарно по пересечению контуров. Выбранный блок имеет высший
приоритет, затем шкаф, столешница и врезная техника; при равенстве остаётся нижний блок.
Попарность важна: длинная столешница скрывает только собственную подпись, но не объединяет
в одну группу две соприкасающиеся тумбы — размеры обеих остаются видимыми.

Привязки и автоматическое вытеснение целиком отключает галочка «Умная расстановка» —
тогда остаётся только сетка 10 мм, а конфликт будет лишь подсвечен валидацией.

### Автоматические столешницы (`shared/utils/countertops.ts`)

Команда «Столешница на ряд» доступна у напольной тумбы, прикреплённой к стене. Рядом
считается последовательность тумб с общей стеной, стороной, задней гранью и отметкой
верха; соседние края должны касаться с допуском `OVERLAP_TOLERANCE = 2 мм`. Навесные
шкафы, пеналы выше 1200 мм, разрывы и пересечения ряд не соединяют.

У автоматической столешницы хранится только связь
`autoCountertop = { supportIds, frontOverhang }` и редактируемое оформление. Длина,
глубина, положение, поворот и высота установки производны от опор:

- длина покрывает ряд от левого до правого края;
- глубина равна самой глубокой тумбе плюс передний свес 40 мм, но не меньше 400 мм;
- низ находится на общей отметке верха тумб;
- `wallAnchor` использует ту же стену, сторону и заднюю грань.

`syncAutoCountertops` вызывается в той же транзакции стора после изменения мебели или
геометрии стен. Новая соседняя тумба расширяет столешницу, разрыв создаёт отдельные
части, а удаление последней опоры удаляет производный объект. Длина одной детали
ограничена 4000 мм; более длинный ряд делится по стыкам тумб без потери покрытия.
Идентификаторы частей сохраняются при повторном расчёте, как и выбранные цвет, толщина
и свес каждой части.

Автоматическую столешницу нельзя перемещать или менять по длине и глубине. Кнопка
«Редактировать вручную» снимает зависимость со всех частей непрерывного прямого ряда,
после чего они становятся обычными независимыми блоками. Это же правило применяется
при удалении одной части длинного ряда, чтобы синхронизация не создала её снова.

### Валидация

Основные правила:

1. Все четыре угла габаритного прямоугольника лежат внутри контура стен (`pointInPolygon`
   по полигону центров стен). Если стен меньше трёх — правило не применяется.
2. Блок не пересекается с другими. Пересечение считается в два этапа: сначала проверяется
   перекрытие диапазонов высот `[elevation, elevation + height]`, и только потом — пересечение
   повёрнутых прямоугольников по теореме о разделяющей оси. Поэтому навесной шкаф над
   напольным и столешница поверх тумб не считаются ошибкой.
3. Блок не перекрывает окно, дверь или сектор открывания двери, если их области
   пересекаются одновременно в плане и по высоте. Поэтому тумба под высоким окном
   допустима, а пенал перед ним — нет.
4. Инженерный вывод не считается физическим препятствием. В зоне доступа 150 мм
   проверяется совместимость сборки: вода и канализация — с базой, содержащей мойку,
   газ — с базой, содержащей варочную панель. Совместимая связь зелёная, недостающая
   или неподходящая — жёлтое предупреждение. Розетка за мебелью сама по себе допустима.
   Для каждой мойки или панели выбирается ровно один шкаф-хост: пересечение проверяется
   и в плане, и по высоте, затем берётся ближайший верх шкафа. Поэтому навесной шкаф над
   той же базой не наследует требования мойки.
5. Пересекающиеся проёмы и инженерные выводы за контуром комнаты помечаются отдельно.

Допуск `OVERLAP_TOLERANCE = 2 мм` обязателен: привязки ставят блоки ровно в касание, и без
допуска состыкованные вплотную блоки подсвечивались бы как пересекающиеся.

Геометрическое нарушение подсвечивается красным в плане, в виде по высоте и в 3D.
Инженерное предупреждение подсвечивается жёлтым; найденное подключение — зелёным.
Подробность показывается в панели свойств.

## 7. Автотесты

Тесты разделены на два слоя:

- **Vitest (`tests/unit/` и `tests/integration/`)** быстро проверяет чистую геометрию, привязки, защитные
  зоны проёмов, инженерные связи, правила валидации и операции Zustand-стора. Общие
  фабрики комнаты, мебели, проёмов и выводов лежат в `tests/fixtures.ts`.
- **Playwright (`tests/e2e/`)** запускает приложение в Chromium и проверяет короткий набор
  критических пользовательских путей: контекстное меню стены и пола, сохранение в
  localStorage, совместимость мойки с коммуникациями, выбор фасада стены и переключение
  умной расстановки.

Тесты геометрии намеренно проверяют поведение на границах: касание не считается
пересечением, высоты учитываются вместе с планом, низкая база допустима под окном,
а высокая мебель вытесняется из проёма и сектора двери. При исправлении ошибки сначала
добавляется минимальный воспроизводящий тест на соответствующем уровне.

`data-testid` используется только как вход в canvas-редакторы, где у Konva нет доступного
DOM-дерева объектов. Все обычные элементы Playwright ищет по роли и видимому названию.
Состояние для сложных E2E-сценариев подготавливается через публичный persist-формат,
а действие и результат всё равно проверяются через интерфейс.

`npm run check` выполняет типы, Vitest и сборку; `npm run check:all` добавляет Playwright.
Отчёт покрытия ограничен критической предметной логикой, а не React-отрисовкой. Текущие
минимальные пороги — 70% statements, 50% branches/functions и 75% lines. GitHub Actions
запускает быстрый и браузерный наборы отдельными задачами на push и pull request.
Окружение CI зафиксировано на `ubuntu-24.04`, а версия Node берётся из `.nvmrc`: это
предотвращает неожиданные миграции `ubuntu-latest` и рассинхронизацию с требованиями jsdom.

Локальный pre-commit установлен через Husky. `lint-staged` прогоняет Oxlint с безопасными
исправлениями и Prettier только по staged-файлам, затем запускаются полный typecheck и
Vitest. Production-сборка и Playwright остаются в `make check`/`make ci`, чтобы hook был
достаточно быстрым для каждого коммита. В CI Husky отключён через `HUSKY=0`.

## 8. Грабли, из-за которых код выглядит именно так

Эти места уже ломались; при рефакторинге их легко вернуть обратно.

1. **`dragEnd` в Konva всплывает.** Перетаскивание блока порождает событие, которое
   доходит до `Stage`. Обработчик панорамы обязан проверять
   `e.target === e.target.getStage()`, иначе смещением вида становятся координаты блока
   и холст «улетает».
2. **Konva не рисует в канвас нулевого размера** (`drawImage ... width or height of 0`).
   Оба редактора монтируют `Stage` только после первого замера контейнера
   (`width > 0 && height > 0`).
3. **R3F на первом кадре может отдать размер 0.** См. `hasSize` в `CameraFit`.
4. **Поля ввода не должны коммитить каждое нажатие.** `NumberField` держит введённый
   текст в локальном `draft` и отправляет значение в стор по blur или Enter (Escape —
   отмена). Иначе стирание числа даёт `Number('') === 0` и блок уезжает в координату 0,
   а промежуточный ввод зажимается по минимуму и мешает набрать число целиком.
5. **Глобальные горячие клавиши обязаны игнорировать поля ввода.** Обработчик
   Delete/Backspace/Escape в `RoomEditor` проверяет `isEditableTarget(e.target)`, иначе
   удаление цифры в панели свойств удаляет сам блок.
6. **Версии React зафиксированы на `~19.2`.** `@react-three/fiber@9` требует
   `react >=19 <19.3`, `react-konva@19.3` — уже `^19.3`; совместимы React 19.2 и
   `react-konva@~19.2`.
7. **Узел Konva обязан возвращаться в позицию модели после перетаскивания.** Konva двигает
   узел сам, в обход React. Если привязка вернула ту же точку, стор не меняется, рендера
   не происходит — и узел остаётся там, куда его дотащили. План показывал блок в одном
   месте, а 3D в другом. Поэтому `FurnitureShape` всегда записывает в узел результат
   `placeBlock`, а не полагается на перерисовку.
8. **Блок, стоящий внутри другого, легко перекрыть чужой гранью.** «Белое дно мойки»
   оказалось верхней гранью корпуса тумбы, проходящей сквозь чашу. Любой блок, в который
   что-то врезается, должен иметь сквозной вырез — и столешница, и корпус шкафа.
9. **Раскладка рассчитана на планшет в альбомной ориентации**: у контейнера
   `min-w-[900px]` и горизонтальная прокрутка. Без этого боковые панели фиксированной
   ширины съедают всё место и холсты схлопываются в ноль.
10. **Дверной проём нельзя вырезать обычным `Shape.holes`.** Его нижняя грань совпадает
    с внешним контуром стены, а Three.js ожидает внутреннее отверстие. Стены собираются
    из секций `panelSegments`; возвращать здесь одну экструзию нельзя без отдельного CSG.
11. **Проём должен нормализоваться в сторе, а не только при отрисовке.** Иначе UI покажет
    зажатое положение, но в localStorage останется невалидный `offset`, ширина или высота.

## 9. Ограничения текущей модели

- Стены — одна цепочка; отдельно стоящая стена искажает контур пола и валидацию.
- Подсвечивается целевая стена, но линий выравнивания и подсветки конкретного соседа,
  к которому блок пристыкуется, пока нет.
- Автоподгон столешницы работает только для прямого ряда одной стены; переход через угол
  и общий угловой шов пока не моделируются.
- Притяжение по высоте смотрит только на блоки, чьи габариты пересекаются в плане:
  выровнять верх двух блоков, стоящих рядом, оно не поможет.
- Мойка и панель исключены из проверки пересечений целиком, то есть их можно поставить
  в воздухе посреди комнаты, и ошибкой это считаться не будет.
- Вытеснение работает вдоль ширины блока: если свободного места в этой линии нет,
  блок остановится на пересечении и просто подсветится красным.
- Размеры и диаметры инженерных выводов пока заданы типовыми константами, а не отдельными
  редактируемыми параметрами конкретного объекта.
- Пересекающиеся проёмы разрешено сохранить: они подсвечиваются как ошибка, а секционная
  геометрия стены остаётся устойчивой. Автоматического раздвигания проёмов пока нет.

## 10. Логичные следующие шаги

1. Линии выравнивания и подсветка конкретного соседа при стыковке.
2. Угловые блоки с двумя стенами и переход столешницы через угол.
3. Редактируемые диаметры труб и типоразмеры монтажной зоны инженерного вывода.
4. Перенос сохранения на Dexie/IndexedDB и список проектов.
5. PWA-обвязка и офлайн-кеш.
